The six findings that decide the design

01

Android has no native MPTCP

Confirmed by Cloudflare's MPTCP write-up. So OpenMPTCProuter's kernel-MPTCP stack cannot run as a normal Android app — it belongs to the pocket-router phase (OpenWrt hardware) and the VPS side, not the phone app. [A18] [A6]

02

mqvpn is the strongest phone-phase candidate

mp0rta/mqvpn (Apache-2.0): userspace, standards-based (MASQUE CONNECT-IP, RFC 9484, over Multipath QUIC), no custom kernel on the VPS, and an official Android client exists — but the project itself marks it experimental (Android 8.0+, F-Droid v0.19.2). [A1] [A5]

03

Single-flow summation is the hard part

One download getting the summed speed needs kernel MPTCP (router only), mqvpn's hybrid stream lane, or packet-level UDP tunnels (MLVPN, Glorytun — no Android clients). Per-connection spreaders like net-merge explicitly do not speed up a single flow. [A2] [A11] [A12] [A13]

04

No-root hotspot sharing has a hard ceiling

Hotspot traffic bypasses the host phone's VPN by default. Working patterns: host-side proxy (partial), proxy + companion client app (transparent for devices that can run it), or root + VPNHotspot (fully transparent, rooted hosts only). [B7] [B9] [B10]

05

Bad path matching can make bonding slower

mqvpn's author documents collapse cases — 0.9 Mbps, ~5 Mbps, ~77 Mbps where ~380 was expected. Scheduler adaptivity (WLB vs MinRTT vs reorder buffer vs reinjection) matters more than any headline efficiency number. [A4] [A3]

06

Only one efficiency anchor is verified

mqvpn's ≈93% of the theoretical sum — and only in the author's emulated tests, not on real phones. [A2] Speedify's often-quoted “up to 95%” could not be found on any Speedify page opened. See Could not verify.

Published failure and recovery cases from the mqvpn author's own measurements — same hardware, different scheduler policy.

Per-option notes

OpenMPTCProuter — schedulers, stack, and the mqvpn convergence

Schedulers: kernel default plus BPF schedulers — BLEST, ECF, redundant (red), round-robin, first, weight, weight-rr, DSCP, backup (bkup), burst, overflow (feeds repo listing + v0.65 release notes). [A7] [A10]

Default stack (Technologies wiki): Shadowsocks-libev carries TCP and Glorytun TCP carries UDP/ICMP, both over MPTCP; alternatives are V2Ray over MPTCP, Glorytun UDP (aggregation without MPTCP), MLVPN, and OpenVPN TCP over MPTCP (slower). Wiki verbatim: “The VPS is needed to combine links connections and access Internet at full aggregated speed.”

Current release v0.65 (2026-11-04) ships kernel 6.18.59, new ECF/BLEST/overflow BPF schedulers — and MQVPN 0.19.0 (xquic built with FEC; MinRTT scheduler by default in OMR's mqvpn config; every mqvpn path bound to a WAN for faster failover). OMR itself is converging on mqvpn as a transport.

Sources: repo · feeds · VPS install wiki · Technologies wiki · openmptcprouter.com

mqvpn — standards, schedulers, benchmarks, failure modes

Standards: CONNECT-IP RFC 9484, HTTP Datagrams RFC 9297, QUIC Datagrams RFC 9221, Multipath QUIC (draft-ietf-quic-multipath), HTTP/3 RFC 9114.

Schedulers & tools: WLB (default — loss/RTT/cwnd-weighted, deficit WRR), wlb_udp_pin, MinRTT; reorder buffer; Reinjection (deadline/idle speculative duplication); Backup FEC (experimental, XOR, ~33% overhead, needs a special build); Redundant Mode (duplicates outgoing UDP only — TCP never duplicated — up to 2× data with 2 paths, 3× with 3; on Android it forces CC = bbr). Congestion control: bbr2 (default) / bbr / cubic / none. TUN MTU default “auto = ~1382”.

Benchmarks (author's, emulated — Proxmox VM / netns / GitHub Actions, not real phones): hybrid lane, symmetric 2×100 Mbit / 25 ms ≈ 187 Mbps at every stream count; asymmetric 300+80 Mbit → 350–357 Mbps at ≥2 streams. SRT 8 Mbps FHD over 2×6 Mbit uplinks: direct VMAF 8.6 with 1.2 s frozen vs mqvpn VMAF 87.7, 0 s frozen. Cutting the 300 Mbit path mid-test dropped throughput 276 → 73 Mbps and the session survived.

Control API: the server exposes add/remove/list users + stats — the node itself issues and manages the user keys Wearless hands to the app (QR / paste). Auth today is PSK over TLS 1.3.

Sources: repo · benchmarks · multipath guide · author blog · F-Droid listing

MLVPN & Glorytun — the packet-level UDP pair

MLVPN: C, libev + libsodium; encryption Salsa20 + Poly1305; privilege separation; weighted round-robin scheduling; loss tolerance configurable. Created 2011, ~584 stars — long-lived, small, low-activity. OMR uses the fork markfoodyburton/MLVPN (new-reorder branch).

Glorytun: AEGIS-256 when AES-NI is present, ChaCha20-Poly1305 fallback; PFS via ECDH Curve25519; keys rotated hourly; built-in path-MTU discovery that does not rely on ICMP (picks the minimum MTU in asymmetric setups); internal MUD scheduler; backup paths (emergency-only) supported; manual traffic shaping.

Sources: MLVPN · Glorytun

Speedify & net-merge — what each actually does

Speedify (from its own support pages): packet-level bonding with server-side reassembly; modes Speed / Redundant / Enhance Streaming; per-connection priorities Automatic / Primary / Secondary / Backup / Never for cost control; AES (hardware) or ChaCha encryption.

net-merge: Go, TUN-based, ~0.18 CPU cores per 100 Mbit/s claimed in its README; works for every app, TCP+UDP, IPv4+IPv6, no proxy setup; if it crashes, networking keeps working. Its own stated Android limits: one connection stays on one network; mobile data stays on; only one VPN app at a time.

Sources: Speedify — How Speedify Works · net-merge

Android platform limits — and the proven workarounds

Each limitation is backed by an opened source (Android documentation or the project that hit the wall). The workaround column lists patterns that demonstrably work; the last column is what still cannot be done.

Hotspot traffic bypasses the host's VPN/TUN by default ShieldShare paper (arXiv:2605.01569); VPNHotspot's entire reason to exist is root-level iptables/ip-rule fixes. [B7] [B9] (1) Host runs a proxy (HTTP/HTTPS/SOCKS5) on the hotspot interface. (2) Companion client app (VpnService + tun2socks → host proxy) makes it transparent. (3) Root + VPNHotspot. Devices that can't run a companion app (consoles, smart TVs) only work via proxy-aware apps, a bridge device, or a rooted host.
Apps ignore proxy settings Every Proxy FAQ: games/streaming apps bypass Wi-Fi proxy config; WhatsApp “deliberately bypasses operating system manual Wi-Fi proxy settings”; HTTP proxy is TCP-oriented. Client must install/configure something. WPAD auto-config is not supported on Android (ShieldShare paper).
Only one VPN can run at a time Android VpnService API reference + VPN developer guide; echoed by net-merge's README. A new VPN deactivates the existing one; user consent required on first connection. [B1] [B2] Wearless's app must be the VPN — integrate the tunnel in-app. ShieldShare's alternative: skip VpnService and proxy in front of another VPN app, accepting proxy limits. Cannot stack Wearless on top of a separate VPN app; some VPN apps block proxy functionality entirely on some devices (ShieldShare repo).
Keeping Wi-Fi + mobile data active simultaneously Android normally tears down the non-default network. Existence proofs: mqvpn's Android app bonds Wi-Fi + cellular via VpnService; net-merge “uses Wi-Fi and mobile data at the same time. No root.” Request the non-default network via ConnectivityManager; pin each tunnel socket with Network.bindSocket() / bindProcessToNetwork(); declare underlying networks on the VpnService Builder. Behaviour varies by OEM/carrier index-only. Keeping both radios up costs battery — mqvpn's author flags this as an open question.
Doze / App Standby kills background networking Android “Optimize for Doze and App Standby” doc: Doze suspends network access, ignores wakelocks, defers jobs/alarms/syncs. [B3] Run the tunnel as a foreground service (FGS apps are not “idle” for App Standby) and request a battery-optimization exemption. The doc itself lists “peripheral device companion app… providing the peripheral device internet access” as an acceptable exemption use case — which matches a hotspot-sharing app. OEM-specific killers (Xiaomi/Samsung etc.) can still kill foreground services index-only. Moblink's README independently tells users to “disable energy saving settings in the phone.”
Foreground-service rules (Android 14+) VpnService API reference; FGS types doc: background-started VPN services get only a temporary allowlist and “must promote itself to the foreground… or the system will shut down the app”; Android 14+ requires a declared foregroundServiceType + matching permission. [B1] [B4] Declare an FGS type. mqvpn ships with type specialUse (F-Droid permission list) — a working precedent for a bonding VPN. connectedDevice / dataSync are the other plausible types. LocalOnlyHotspot gives a LAN with no internet Android LocalOnlyHotspot doc (page updated 2026-11-16): “the network created won't have Internet access”; one reservation per app; Android 13+ needs NEARBY_WIFI_DEVICES, older targets need ACCESS_FINE_LOCATION (maxSdkVersion 32). [B5] Use LocalOnlyHotspot (or a Wi-Fi Direct group) only as the local link between host and companion clients — never as the internet path. The internet-facing AP must be the user-enabled system hotspot, or the tunnel terminates on the host and is re-shared via proxy. No API exists to switch on the system hotspot programmatically — ShieldShare's design guides the user to enable it manually.
No-root client accounting is blind ShieldShare repo README “Critical Limitations”: apps cannot read /proc/net/arp or hotspot system files, so ARP-based client detection is impossible. Account at the proxy layer (ShieldShare: per-client stats in a Room DB, quota enforcement/blocking) or at the TUN layer for companion-app clients. Client detection then takes 30 s–1 min via traffic; proxy-layer accounting only sees proxied traffic — un-proxied traffic is invisible and unbillable.
Wi-Fi Direct group limits (companion pattern) Hotspot-Bypass-VPN README: 256 total / 128 per-client connections; host SSID DIRECT-HotspotBypass, proxy at 192.168.49.1:8080. Foreground service + WakeLock + AlarmManager restart for persistence (same README). Consoles can't connect directly (no SOCKS5 support) — the project routes them via its Windows client's sharing instead.

The three sharing architectures, ranked by transparency

1

Root — VPNHotspot rooted hosts only

iptables/ip-rule routing of hotspot clients into the TUN. Fully transparent, all protocols, plus client monitoring/blocking. Mygod/VPNHotspot, Apache-2.0, Android 10–17. github.com/Mygod/VPNHotspot

2

No-root, companion-client recommended for Wearless

Host: hotspot or Wi-Fi Direct group + SOCKS5 proxy whose upstream is the host's bonded tunnel. Client: Wearless app in “client mode” (VpnService + tun2socks) pointing at the host. Proven by two independent implementations: Hotspot-Bypass-VPN (MIT; Android 7.0+; client MTU 1350; repo-claimed 10–40 Mbps / +30–60 ms — the project's own claims, not independently verified) and Every Proxy (proprietary; FAQ documents Tun2Socks client mode + SOCKS5 UDP ASSOCIATE).

3

No-root, proxy-only — the ShieldShare model

Zero client installs beyond proxy config / QR / PAC; per-user accounting and quotas; but partial coverage — proxy-aware apps only. Sources: ShieldShare paper · repo (design reference only — no license).

A shipping product proves this model in the wild: NetShare (NetShare Softwares) is a no-root tethering app whose own FAQ states that “because Android system limitations prevent direct routing of internet traffic without root, NetShare uses a local proxy server to route the internet data from your connected device through the host device” — clients must set up a proxy on their device. It also bypasses carrier tethering limits and secures the hotspot with WPA2. [B11]

Findings 4

Feature ideas worth copying — capabilities only

Behaviours proven by existing products, stripped of their branding. Each names the source it was read from.

  • Three bonding modes — Speed / Redundant (duplicate packets across links, first arrival wins, explicitly costs more data) / Streaming (auto-detect streaming traffic incl. SRT by packet inspection; prioritization, secondary-link boost, automatic redundancy). mqvpn independently converged on the same trio (WLB / Redundant Mode / FEC+reinjection for SRT) — a strong signal these are the right three modes. Source: Speedify support + mqvpn multipath guide.
  • Pair & Share — devices on the same LAN share their 4G/5G bidirectionally and simultaneously; discovery + pairing request/accept flow; per-device permissions (share to / use from / backup-only); each shared connection capped at 10 Mbps by default and forced to Secondary priority; paired-device data-usage stats (shared vs received). Source [A15]: Speedify Pair & Share.
  • Cost controls — per-connection priority (Automatic / Primary / Secondary / Backup / Never); per-connection daily and monthly data caps; overlimit behaviour is a choice — stop using the connection entirely, or switch it to a reduced speed; an optional per-connection rate limit; a warning at 75% of the monthly cap; at 100% the app stays connected but stops using that connection and prompts the user; daily-cap guidance ≈10% of the monthly cap (example given: 2 GB monthly → 200 MB daily); cellular connections default to Secondary priority, with Backup available; usage is only tracked while connected to the Speedify VPN. If the user opts into limits at install, the defaults are 2 GB per month and 200 MB per day on cellular. Sources [A20] [A21]: Speedify Data Limits articles. OpenMPTCProuter's omr-quota adds a good open-source variant: a “block” action that keeps the WAN up but never cuts the last working WAN.
  • Wi-Fi repeater mode + Share VPN — re-broadcast an existing Wi-Fi connection (not just cellular), and share the host's active VPN connection itself to connected devices — both shipped by the no-root NetShare app on top of its local-proxy design. Source [B11]: netshare.app.
  • QR-code joining — the QR encodes proxy address/port/optional credentials + a local help page / PAC URL; per-client data quotas with enforcement/blocking; per-client accounting dashboard with export. Sources [B7] [B8]: ShieldShare paper + repo.
  • Live per-link quality monitoring — mqvpn 0.19.0's Android dashboard has live speed and reordering charts and per-network on/off switches (Wi-Fi / mobile / Ethernet / Bluetooth). Copy this UI pattern.
  • Automatic failover with configurable return-to-master (immediate / delayed / manual) and per-interface “monitor only” mode — OpenMPTCProuter's omr-tracker, per v0.65 notes.
  • Built-in speed test against the bonding server — OMR ships luci-app-iperf + SpeedTestC in its feeds.
  • One-tap server-side provisioning — a control API (mqvpn's) issues a user; a key is handed out, the app pastes/scans it, done. This is exactly Wearless's key model: the node issues the key, and the user scans the QR or pastes it into the app.
Findings 5

Speed-optimization checklist — verified items only

Seven rules, each traceable to an opened source. Anything that circulates only in secondary blogs (TCP-over-TCP loss percentages, WireGuard overhead byte-tables) was excluded — see Could not verify.

  1. Transport must be UDP-based; never tunnel TCP over TCP. mqvpn is QUIC/UDP end-to-end. OpenMPTCProuter's own docs rank OpenVPN-TCP-over-MPTCP as the slow option, and mqvpn's author cites OMR issue #3067, where UDP throughput collapsed (~140 → ~50 Mbps) when carried over a TCP-based multipath stack. Retransmission stacking (“meltdown”) is the mechanism.
  2. Set the TUN MTU deliberately and clamp MSS. Verified anchors: mqvpn's TUN MTU default is “auto = ~1382” (repo config); Hotspot-Bypass-VPN's tun2socks client uses MTU 1350; Glorytun performs PMTU discovery without ICMP and picks the minimum MTU across asymmetric paths, avoiding ICMP black holes. Measure on target carriers instead of trusting blog tables. [A1] [B10] [A12]
  3. Scheduler policy must be adaptive. Similar paths → WLB. Jitter / moderate RTT gap → WLB + reorder buffer (without it: 0.9 Mbps collapse; with it: 37.6 Mbps in the same test). Strongly asymmetric paths → MinRTT (212 vs ~77 Mbps). Link failure mid-flow → Reinjection. Lossy live streaming → Backup FEC (experimental, ~33% overhead) or Redundant Mode (up to 2× data).
  4. Congestion control: BBR2 by default. mqvpn defaults to BBR2 per path (bbr / cubic / none selectable); Redundant Mode on Android forces BBR.
  5. Prefer AEAD ciphers with hardware acceleration. Glorytun uses AEGIS-256 when AES-NI is available, ChaCha20-Poly1305 otherwise — relevant on phones without AES instructions. Avoid double encryption (tunnel inside tunnel). No trustworthy cross-protocol overhead benchmark was found in opened sources.
  6. VPS placement and sizing decide the ceiling. OMR's wiki demands the “lowest latency as possible” between router and VPS and ≥1 GB RAM on KVM for its stack; mqvpn's server is a plain Linux binary with UDP 443 open — far lighter. In all designs the VPS must carry the full aggregated throughput in both directions, so VPS bandwidth (not CPU) is the usual ceiling; the VPS's own uplink must exceed the sum of the client links.
  7. Set honest expectations: 85–93% under good conditions. ≈93% of the sum was reached only in mqvpn's emulated hybrid-lane tests; a single raw-mode TCP flow gets ~one path (96 of a possible 200 Mbps); per-connection balancers reach the sum only across many connections. Build explicit “bonding is slower than your best single link” detection with auto-fallback to MinRTT / best-path — the collapse cases are documented, not hypothetical.
Discoveries

New approaches found during research ★

Ideas that go beyond copying existing products. Each carries an honest status — proven, proven-in-a-niche, or design proposal. Nothing here is promised as shipped technology.

★1 Hybrid TCP lane — lwIP termination → HTTP/3 streams

proven in author's emulated benchmarks

The answer found for true single-flow summation on Android without kernel MPTCP. mqvpn embeds a userspace TCP stack (lwIP) on the client, terminates inner TCP flows, and relays each as an ordered HTTP/3 stream that Multipath QUIC can stripe across paths. Measured by the author: single TCP flow 96 Mbps (raw) → 187 Mbps (hybrid) on 2×100 Mbit. Shipped in mqvpn ≥0.9.0 and enabled by default in its server installer; the Android client that uses it is still marked experimental. Sources [A2] [A1] [A4]: benchmarks · repo · blog

★2 Companion-client pattern for no-root hotspot sharing

proven pattern

Accept that the host side can only offer a proxy, and make sharing transparent by putting a VpnService+tun2socks client on each client device pointed at the host's proxy. Proven by two independent implementations (Hotspot-Bypass-VPN, MIT; Every Proxy Tun2Socks mode). Architecturally the same trick as Speedify Pair & Share and Moblink's relay: the second device runs software too. Wearless should ship host mode and client mode in the same app. Per-project performance claims remain unverified.

★3 Adaptive scheduler policy engine

design proposal — experimental

Instead of one scheduler, switch WLB / WLB+reorder / MinRTT / reinjection from live per-path RTT-loss-jitter measurements, using the mqvpn author's published failure cases as the test fixtures. This is the realistic route to staying near ~93% and avoiding slower-than-single-link outcomes. The components all exist in mqvpn (Apache-2.0); the auto-switching policy itself is a design proposal grounded in the author's data — not a shipped feature.

★4 Spare-phone relay (Moblink / SRTLA pattern)

proven for SRT only

A second phone contributes only its cellular uplink as an extra path: the relay app binds its outbound socket to the cellular network while receiving stream data over local Wi-Fi. Generalizable beyond SRT: a Wearless “relay mode” where any spare phone becomes a path donor (cf. Pair & Share). Proven in the IRL-streaming niche for SRT traffic only; the general-traffic version is a design proposal. Sources [C11] [C10]: moblink · srtla

★5 Network coding (RLNC) instead of retransmission / reordering

research direction only

Coded packets are interchangeable, so path reordering and head-of-line blocking largely disappear in theory. Code On Technologies markets this for multipath (vendor claims of order-of-magnitude gains — no independent verification found). [A19] Steinwurf's Kodo is not free software index-only. mqvpn's XOR Backup FEC is the available open building block in this direction. Do not promise it.

★6 Application-layer segmented downloads (HTTP range requests)

index-only

Split one file into parallel range fetches, one per interface; needs no VPS at all but only accelerates cooperating download traffic. A candidate for a Wearless “accelerated download” feature, not the core tunnel. (Kaspar et al., IEEE ICC 2010 — paper not opened in this pass.)

★7 Android 16 Linux Terminal VM with MPTCP

unverified — curiosity only

A social.kernel.org post claims Android 16's Terminal Debian VM runs kernel 6.1 with MPTCP while the host OS still lacks it. Even if true, VM traffic is not the phone's app traffic, so it is not a viable Wearless path.

Conclusion

Recommended open-source stack

What the evidence supports building on — phone first, router later, one server fleet for both — and in both phases the node issues the key (QR / paste).

Phase 1 — Android app + VPS ship this first

  • Data plane: mqvpn (mp0rta/mqvpn, Apache-2.0), forked or consumed as a library. Server on a plain Linux VPS (Ubuntu 22.04 / Debian 12, UDP 443) — no custom kernel, unlike OpenMPTCProuter. Enable hybrid mode + reorder buffer by default; scheduler policy per ★3. The server's Control API (add/remove/list users, stats) is the integration point for Wearless API keys. [A1] [A3]
  • Android app: own VpnService front-end (one Start button), min Android 8.0 (API 26) to match mqvpn/net-merge precedent; foreground service with declared type (specialUse precedent from mqvpn; expect Play policy scrutiny); battery-optimization exemption onboarding flow; per-network toggles + live speed/reorder charts (copy mqvpn 0.19's dashboard pattern).
  • Hotspot sharing: host mode = system hotspot (user-enabled; no API exists) or Wi-Fi Direct group + built-in SOCKS5 proxy (sing-box, GPL-3.0+clause, or hand-rolled) whose upstream is the mqvpn TUN; client mode = same app with VpnService+tun2socks → host proxy (★2). Per-client accounting/quotas at the proxy layer (ShieldShare design, original code — its license forbids copying). Rooted-host optional mode: integrate/study VPNHotspot (Apache-2.0).
  • Keys: the node issues the key — the node installer / its localhost Control API creates the per-user PSK and presents it as a QR code; the user scans the QR or pastes the key into the app. Revoking a user on the node (remove_user) disconnects it immediately. frp (Apache-2.0) for exposing/managing nodes behind NAT where needed.
  • Fallbacks: WireGuard (Apache-2.0 Android library) as a single-path fallback transport; AmneziaWG (MIT / Apache-2.0) where DPI blocks plain WireGuard/QUIC.

Phase 2 — Pocket router

  • OpenMPTCProuter (GPL-3.0) on OpenWrt hardware with its VPS image: kernel MPTCP + BPF schedulers (BLEST / ECF / redundant) and mqvpn 0.19 — the same mqvpn data plane as Phase 1, so one server fleet serves both phone and router, and the node issues the key in both cases.

Explicitly not recommended

  • Wifi Scaler — proof-of-concept, no repo.
  • MLVPN / Glorytun as Android data planes — no Android clients; keep for router/VPS experiments.
  • net-merge as the core — no single-flow bonding (but its no-server per-connection mode is a legitimate “offline fallback” feature).
  • ShieldShare code — no license; design reference only.

Proof gate

Phase 0 — the real-device test that is still owed

The one gap research alone cannot close: no mqvpn speed number in this document was measured on a real phone — every figure is the author's emulated (VM / netns) test. not yet measured This section is the exact protocol for closing that gap, so the test can be run as written and its results dropped into the table below. It needs two things only the project owner can supply: a real Android phone in hand, and a VPS to run the bonding server on.

Setup — fixed for every run

  • Server: mqvpn server on a plain Linux VPS (Ubuntu 22.04 / Debian 12, UDP 443, no custom kernel) [A1], placed at the lowest latency available to the phone's connections — VPS placement decides the ceiling (checklist item 6). The VPS uplink must exceed the sum of the phone's links, or the VPS — not the bonding — becomes the bottleneck.
  • Client: the official mqvpn Android app (Android 8.0+, F-Droid v0.19.2, marked experimental) [A5] on the test phone, with Wi-Fi and mobile data both active.
  • Mode: hybrid mode + reorder buffer enabled — the configuration behind the ≈93% lab figure [A2] [A3]. Battery-optimization exemption granted to the app first, so Doze cannot kill the tunnel mid-test [B3].
  • Fairness: all three measurements back-to-back, same phone position, same server, same test target — otherwise the numbers are not comparable.

The three measurements

  1. Wi-Fi alone — mobile data off; single download/stream through the tunnel over Wi-Fi only. Record the sustained Mbps.
  2. Mobile data alone — Wi-Fi off; the same test over cellular only. Record the sustained Mbps.
  3. Bonded — both radios on, one single download/stream (not several parallel connections — per-connection spread does not count, see [A13]). Record the sustained Mbps.

Pass criteria

  • Bonded > best single link. If the bonded number is at or below the better of the two single-link numbers, bonding has failed on real hardware — the documented collapse cases (0.9 Mbps under jitter, ~77 Mbps on asymmetric links) show this is a real outcome, not a formality [A4].
  • Compare against the sum, honestly. Report bonded ÷ (Wi-Fi + mobile) as a percentage, next to the lab anchor of ≈93% — and publish whichever number the phone actually produces, even if it is far lower.
  • Repeat with the scheduler switched. Run the bonded test once on WLB (default) and once on MinRTT [A3]; on asymmetric real-world links the author's data says the choice can be worth more than the bonding itself (~77 vs ~212 Mbps in his test).
  • Session survives a link drop. Kill Wi-Fi mid-download: the session should continue on cellular, as it did in the author's path-cut test (276 → 73 Mbps, session alive) [A2].

Architecture: Kotlin + engine library, not Flutter-first

Evidence from real projects all index-only: WireGuard Android = Kotlin UI + Go engine built as libwg-go.so via JNI/CGO, VpnService hands the TUN fd to Go. sing-box Android = Go libbox (gomobile) inside a Kotlin VpnService, TUN delivered via PlatformInterface.openTun. Conclusion from the evidence: every serious tunnelling app keeps the data plane in a native/Go library behind a thin platform VpnService; the only question is the UI shell. Flutter (the Hiddify pattern) is proven for the shell and buys desktop parity later, but the TUN/VpnService glue is Kotlin platform-channel code either way. For a one-person, Android-first V1, native Kotlin + the engine library is the lower-risk reading of the evidence; Flutter becomes attractive when Wearless ships desktop clients. Resource Monitor — new V1 feature owner's order · 18 Nov 2026

The app gets a dedicated Resource Monitor screen that shows, live, how much of the phone the Wearless app itself is using — as much as Android exposes to an app about itself, no root. This is also the instrument that closes the battery gap above: since no published bonding battery number exists, Wearless measures its own cost on the device, while it runs.

  • RAM — the app's own memory use (PSS / RSS), plus total device RAM and currently available RAM for context.
  • CPU — the app's own CPU use (current % and a short live history/graph), so the cost of the tunnel + bonding engine is visible, not guessed.
  • Battery — battery level, charging state, and the app's drain while bonding runs (rate / session cost where Android reports it).
  • Temperature — device / battery temperature and Android's thermal status, so throttling risk during long bonded sessions is visible.
  • Per-link data — bytes up / down per connection (Wi-Fi, mobile data, each bonded path), per session and in total — the same per-path view the node heartbeat reports on the server side.
  • Everything else Android exposes about the app itself — e.g. app storage/cache size, uptime of the tunnel service, and per-path RTT / loss alongside the resource figures.

Honest limit: Android only lets an app see a bounded set of figures about itself — some values (exact per-app battery drain, some temperatures) are estimates, sampling-based, or vary by device/OEM. The screen shows what the platform actually exposes on that phone and labels estimates as estimates; it does not invent precision Android does not provide.

Patterns that repeat across ≥3 projects (the reliable design core): (1) One-time enrolment secret, permanent identity afterwards (NetBird setup key → stored peer key; Newt ID+secret; Tailscale auth key → node key) — the secret is for joining, not for every connection. (2) Outbound-only agents win (Newt, NetBird dial out and hold a persistent stream — no inbound ports on the agent host, NAT-friendly; Wearless's node is the inverse case — it is the public listener, and it is managed locally on the box (its Control API never leaves localhost)). (3) Heartbeat = identity + version + state summary, not a metrics firehose (EasyTier's field list is the model). (4) Config is pushed, not edited on the box. (5) systemd Restart=always + start-on-boot is the universal boring answer. (6) Metrics are Prometheus-shaped even in small projects (frp, mqvpn exporter).

The Wearless node agent — V1 feature list (each item traces to a pattern above)

Key flow: the node issues the key. The installer creates the node's users locally (per-user PSKs, applied via the localhost Control API), and each key reaches its user as a QR code / pasted key for the app. The node's status is kept locally on the box and is visible to the app when connected. There is no website, account system or remote sync anywhere in this design.

  • A single mqvpn server process + a small Wearless agent wrapper — the wrapper is needed because mqvpn has no outbound heartbeat, no self-update and no remote management link (verified absence in its docs).
  • Enrolment: the node issues the key. The installer creates each user on the node itself — a per-user PSK applied through the localhost Control API (add_user/remove_user) or the config file — and presents the key as a QR code; the user scans the QR or pastes the key into the app. Removing a user on the node disconnects its sessions. The Control API never leaves localhost (verified: unauthenticated, binds 127.0.0.1 by default).
  • Status record (kept locally on the node; readable on the box and shown to the app on connect): node ID, agent + mqvpn version, uptime, OS/arch, total RAM, agent RSS (this is how Wearless gets the memory number below for real), active sessions count, per-user bytes up/down (from get_stats), per-path RTT/loss for active clients (from get_status), config version applied, last error. Field set modelled on EasyTier's HeartbeatRequest + mqvpn's own stats.
  • Config: users, scheduler minrtt|wlb|backup_fec, CC bbr2, MaxClients — all real mqvpn knobs, verified — are set in the node's local config / via the localhost Control API, with the applied config version recorded in the status record.
  • Start-on-boot + watchdog: systemd unit, Restart=always (the Newt pattern).
  • Logging/metrics: journald locally; a Prometheus-format endpoint on localhost for local monitoring via the agent (the mqvpn exporter pattern); no user content logging.
  • Multi-user: mqvpn per-user PSKs natively; the node's own user list — created on the node and applied via the Control API — is the source of truth for who exists.
  • Later: signed self-update with rollback (no surveyed small project documents this well — Tailscale/NetBird ship via package managers; treat OTA as a Later item and say so), a remote diagnostics job channel (NetBird's gRPC Job stream is the model index-only), an exit-node-style “also route the LAN behind this node” mode (the Tailscale subnet-router pattern index-only).

The answer, by node type

Lightweight proxy node (no bonding): YES, comfortably, on published numbers. Kernel WireGuard (~0.5 MB slab) + microsocks (<1–4 MB) or Tinyproxy (~2 MB) totals single-digit MB for the data plane; even adding a Go agent, the frps precedent (28 MB idle) and sing-box (21 MB idle) sit far under 100 MB. A 128 MB host is realistic for this tier; the OS, not the proxy, becomes the budget item.

Full mqvpn bonding node: SOFTWARE FITS AT IDLE — MEASURED; UNDER LOAD STILL OPEN. Wearless's own lab ran the mqvpn v0.19.2 server and measured idle RSS ≈ 36 MB, and the server stayed alive and healthy — its Control API answering status queries — under a hard 48 MB total memory cap lab-tested [D11]. So the bonding-node software itself fits a 100 MB budget; the operating system is the deciding item. Supporting context: mqvpn ships in OMR router firmware (routers are 128–512 MB total devices) and its authors explicitly engineer per-platform memory budgets. Caution that remains: userspace QUIC + multipath buffering under real traffic is categorically heavier than idle — a different MASQUE implementation (Cloudflare WARP's) is described by the MicroWARP project as “tens–hundreds of MB” index-only, analogue only — not mqvpn, and wireguard-go shows how userspace networking can balloon under load if queues are uncapped. No under-load mqvpn number is claimed anywhere in this report.

Does mqvpn run on a 128 MB-total-RAM OpenWrt router via OMR? OMR targets many routers and includes mqvpn, but no source found names a 128 MB device running mqvpn specifically — OMR's own hardware guidance trends to 256 MB+. Could not verify.

Proposal — practical V1 rule Ship two node tiers: Node Lite (proxy/WireGuard, ≥128 MB hosts) and Node Full (mqvpn bonding).
